Architecture Overview

We designed our software architecture before writing code. Here are the key concepts we applied:

Module Identification

Break the game into logical subsystems with hidden implementations and clear APIs.

Relationship Graphs

Visualize which modules depend on each other and in what direction.

CRC Cards

Class-Responsibility-Collaboration cards define what each module does and who it talks to.

Activity Diagrams

Map out the program's workflow — the update loop, decisions, and parallel paths.

Avoid Cyclic Dependencies

Prevent modules from referencing each other in circles — break them with controllers.

Team Division

Each programmer owns a module and collaborates on shared APIs at the edges.

Role of the Lead Programmer

Someone must make high-level architecture decisions before anyone writes code.

  • Split classes into modules with clear boundaries
  • Choose computation model — fixed timestep physics loop
  • Define data files — level schemas in levels.py
  • Select libraries — Pygame for rendering, Pymunk for physics
We agreed on modules and APIs first, then divided the work. This prevented duplicate code and missing features.

Each owner had final say on their module's implementation. We held interface parties to agree on shared APIs.

CRC Cards: Engine Layer

The simulation layer — physics handles the math, entities define gameplay objects, types.py is their shared contract.

physics.py (PhysicsWorld)
Responsibilities
  • Create rope chains with PinJoints
  • Cut ropes by removing joints
  • Detect collisions & queue callbacks
  • Winch length adjustment API
  • Step simulation with sub-steps
Collaborations
  • Pymunk library (delegated solver)
  • game.py (collision callbacks)
  • types.py (collision type constants)
entities.py (Pure Model)
Responsibilities
  • Candy: dynamic body + squash/stretch
  • Target: sensor + swallow animation state
  • Anchor variants: static, magnet, slider, winch
  • Hazards: spike, teleport, spider
  • No drawing code — pure data + physics
Collaborations
  • types.py (collision type constants)
  • game.py (registers into physics space)
  • entity_renderer.py (provides positions)
  • config.py (reads physics constants)
types.py holds CT_CANDY, CT_TARGET, CT_SPIKE, CT_TELE_A, CT_TELE_B and GameState — the shared constants that physics.py and entities.py both import. This eliminates duplicate definitions and prevents drift.

Activity Diagram: Win/Lose Flow

Decision guards in our loop

After each physics step, collision callbacks check conditions:

  • [candy in target + speed < 80] → start 2s settle timer
  • [settle complete] → transition to WON
  • [candy hits spike] → transition to LOST
  • [spider reaches candy] → transition to LOST
  • [candy out of bounds] → transition to LOST

Synchronization points

We use deferred post-step actions — no space mutation during the solver step:

Physics step completes
Callbacks fire safely
State mutations happen
Renderer sees final state

Avoiding Cyclic Dependencies

If Module A references B, and B references A, you have a cycle. Here's how we break them:

Problem Pattern

Shared collision constants

Both physics.py and entities.py need the same collision type numbers. If each defines them, values can drift. If they import each other, you get a cycle.

entities.py  <-->  physics.py
  (cyclic if they import each other!)
Our Solution

Shared types.py + game.py as mediator

types.py holds shared constants. game.py acts as the controller — entities and physics never import each other.

types.py (CT_CANDY, CT_TARGET, ...)
    ↺         ↺
entities.py    physics.py
    (no cycle! shared contract)
Our rules: (1) physics.py never imports entities.py — game.py wires them. (2) Shared constants live in types.py — single source of truth. (3) View modules never import Controller modules.

Data-Driven Level Design

Level schema

Levels are defined as dictionaries — not hardcoded. New levels require data edits, not engine rewrites.

{
  "name": "Double Swing",
  "candy": (360, 900),
  "target": (200, 250, 30),
  "anchors": [{"x":260,"y":1100,"letter":"A"}],
  "spikes": [...],
  "teleports": [...],
  "spiders": [...]
}

Tooling pipeline

Level editor creates data
Validator checks bounds
Factory loop builds entities
Game runs the level
Separation of authoring and runtime means designers iterate without touching engine code.

Key Takeaways

01

Design before you code

CRC cards and activity diagrams helped us agree on module boundaries before writing a single line. This saved us from duplicated work and missing features.

02

Keep modules independent

Each module hides its implementation behind an API. Physics doesn't know about UI. Entities don't know about rendering. This makes changes safe and local.

03

Use a controller to break cycles

game.py mediates between physics and entities. No module imports its sibling — the controller wires everything together.

04

Data-driven beats code-driven

Levels are schemas, not source code. Our level editor and validator sit outside the engine, letting content scale without touching the simulation.
