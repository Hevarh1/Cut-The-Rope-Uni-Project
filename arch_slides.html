System Architecture

From app flow to physics constraints and rendering boundaries.

1) Module Boundaries and Dependency Flow

run.py

  • App.run() clamps dt and owns frame cadence.
  • App._handle_event() routes raw input by active screen state.

Boundary: application shell only, no simulation rules.

src/game.py

  • Game._create_entities() builds anchors, hazards, teleports, and ropes.
  • Orchestrates update order: input effects, mechanic logic, physics step, draw handoff.

Boundary: gameplay orchestration and level lifecycle.

src/physics.py

  • setup_collisions() binds candy interactions to callback hooks.
  • create_rope(), cut_rope_by_letter(), and winch adjust APIs own topology changes.

Boundary: solver constraints and contact handling only.

src/entities.py

  • Each entity encapsulates local state, update behavior, and draw contract.
  • Includes target swallow states, anchor variants, teleport pairs, and spider behavior.

Boundary: reusable gameplay objects with explicit responsibilities.

src/renderer.py + src/ui.py

  • Renderer owns virtual canvas scaling, particles, and background composition.
  • UI screens (title/select/guide/custom) remain independent from physics internals.

Boundary: presentation layer consumes state but does not author physics.

src/levels.py + src/savedata.py

  • levels.py defines campaign schemas and mechanic combinations.
  • savedata.py encapsulates score stars, best times, and custom level IO.

Boundary: data contracts support fast content iteration.

2) Fixed Timestep: Determinism for Puzzle Consistency

Core simulation rhythm

accumulator += dt_render
while accumulator >= dt_physics:
    space.step(dt_physics)
    accumulator -= dt_physics
  • PhysicsWorld.step(dt) uses sub-steps from PHYSICS_STEPS.
  • Collision side effects run after stepping through the deferred action queue.

In code: PhysicsWorld.step(dt) in src/physics.py and frame loop from App.run().

Why architecture cares

Determinism: same level solution remains reliable across machine speed.
Stability: rope constraints are solved in predictable sub-steps.
Fairness: timing challenges stay design-driven, not frame-rate driven.
Tuning: PHYSICS_STEPS in config controls precision-cost tradeoff.
Debugging: reproducible cut sequences simplify bug isolation and balancing.
Balancing: gravity and rope constants remain stable across hardware classes.

3) Event and Collision Routing Pipeline

Input route

run.py: App._handle_event() dispatches by active screen, then Game.handle_event() handles rope cuts, slider drag, and winch controls.

Contract: UI states consume their own events; gameplay input executes only in PLAYING.

Collision route

PhysicsWorld.setup_collisions() binds candy collisions to callbacks, then queues safe actions after stepping.

Contract: no space mutation during space.step(); only deferred callbacks mutate state.

State mutation

Callbacks trigger _on_candy_target(), _on_candy_spike(), teleport handlers, and transition game state.

Contract: transition authority is centralized in game handlers, not distributed across rendering code.

Feedback layer

Renderer receives resulting visual effects through particle bursts and animation triggers, keeping simulation and visuals decoupled.

Contract: visuals react to outcomes; they never define win/lose conditions.

Key architectural choice: deferred post-step actions prevent illegal physics-space mutation during active solver execution.

4) Layered State Machines

Application screen state

title -> level_select -> game -> guide/custom
  • Menu screens stay UI-only and avoid physics dependencies.
  • Entering gameplay always instantiates a fresh Game object.

Owner: App.screen in run.py.

Gameplay state

PLAYING -> WON or LOST
  • Collision callbacks and spider catches are the primary transition triggers.
  • WON/LOST freeze core interaction and drive overlays.

Owner: GameState in src/game.py.

Entity micro-state

STATE_IDLE -> STATE_SWALLOWING -> STATE_DONE
  • Target swallow animation progresses by timer, independent of solver timing.
  • Done state prevents duplicate collection reactions.

Example: target animation state machine in src/entities.py.

Anchor behavior state

inactive -> active -> cut/deactivate
  • Magnets activate by radius check and spawn rope topology dynamically.
  • Winches retain active + current_length for continuous adjustment.

Magnets and winches act as small localized state machines.

5) Data-Driven Levels and Entity Factory

Level schema (src/levels.py)

{
  "name": "Double Swing",
  "candy": (360, 900),
  "target": (200, 250, 30),
  "anchors": [{"x":260,"y":1100,"letter":"A"}],
  "spikes": [...],
  "teleports": [...],
  "spiders": [...]
}
  • Each top-level key maps to one mechanic family and creation path.
  • Schema keeps new level content decoupled from engine rewrites.

Runtime translation (Game._create_entities())

for ad in level["anchors"]:
    a = Anchor(...)
    rd = physics.create_rope(...)

for td in level["teleports"]:
    tp = TeleportPair(...)

for sd in level["spiders"]:
    sp = Spider(...)
  • Factory loops instantiate objects, register physics bodies, and store rope references.
  • Missing optional keys get defaults before use to preserve runtime safety.
Architecture impact: content iteration happens through data edits, not engine rewrites; this is the core Lecture 4 data-driven pattern.

6) Persistence and Tooling Boundaries

Persistence API

  • save_level_score() updates best-time records and star outcomes.
  • load_custom_levels() and related APIs isolate file format concerns.

Single persistence boundary keeps gameplay logic storage-agnostic.

Authoring Tool

  • level_editor.py enables mechanic placement and exportable level data.
  • Designers can iterate level intent without touching solver or renderer code.

Tooling extends content pipeline without altering runtime architecture.

Validation Layer

  • validate_levels.py checks bounds, overlap hazards, and target safety.
  • Acts as design-time guardrails before levels hit runtime execution.

Early validation reduces unstable or unfair content states.

Separation of runtime and authoring concerns keeps the game loop lean and iteration speed high.

7) Rendering Boundary vs Simulation Boundary

Simulation side

  • Pymunk world in PhysicsWorld is the authoritative source of motion and collisions.
  • Game logic mutates state and constraints through explicit APIs only.
  • Coordinate conversion utilities bridge Pymunk and pygame spaces.
  • Deferred post-step actions isolate side effects from solver lock phases.

Presentation side

  • Renderer owns virtual canvas scaling and background composition.
  • ParticleSystem and StarField provide non-authoritative visual feedback.
  • UI screens are independent views over game progress and save data.
  • window_to_virtual() keeps input mapping stable on resize.

Result: visual polish can evolve without destabilizing gameplay physics behavior.

8) Lecture 4 Recap: Patterns Used in This Game

Layered architecture

  • Runtime shell, gameplay orchestration, simulation, and rendering are separated.
  • Each layer can evolve with minimal cross-module regression risk.

Event-driven design

  • Input and collisions route through explicit handler boundaries.
  • Deferred callback execution protects physics consistency.

State machine modeling

  • Screen, game, and entity states each own local transition rules.
  • Centralized transitions prevent circular logic and hidden side effects.

Data-driven extensibility

  • Schema-based levels and tooling scale content throughput.
  • Persistence contracts stabilize progression without engine rewrites.
